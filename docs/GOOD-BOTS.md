# Good bots

> **A ban can be lifted. An AbuseIPDB report cannot be deleted.** This page answers
> one question with measurements instead of intent: *does this project block search
> engines and AI crawlers?* — and what stops a mistaken ban from becoming a public
> accusation.

Measured on the three production hosts on 2026-11-01 with
`tools/audit-good-bots.sh` (read-only; it changes nothing).

The 4xx are 404/410 for URLs that do not exist — normal for a crawler. The **503s are
rate limits**: `limit_req` answers a throttled request with 503, not 403. That is not
a ban and it is not fail2ban, but it is what a crawler sees as "slow down": 39
responses in a week across all bots, `PerplexityBot` the most (7).

## Why nothing is blocked today, and what could change that

The filters are **path-based**, not user-agent based:
`nginx-attack-scan` matches `/.env`, `/.git/`, `phpmyadmin`, `/actuator` and similar
probe paths; `nginx-wp-login` matches `POST wp-login.php`; `nginx-php-probe` matches
`Primary script unknown`. A crawler requesting real pages never matches. No jail in
this estate reads the `User-Agent` at all, and nginx has no user-agent rules either.

The one path that *could* ban a crawler is **`nginx-forbidden`**: it fires on
`access forbidden by rule` (a 403 from nginx) ten times an hour. A site that adds a
`deny` rule for a path Google still follows would feed that jail. It has not happened
— zero 403 for bots in a week — but it is one config change away.

The escalation makes a mistake expensive: on 5.35 `bantime.increment = true` with
`factor = 2` and `maxtime = 12w`, plus `recidive` at 4 weeks. A crawler that trips a
jail five times is banned for months.

## The rail: never report a crawler

New in 1.6.0, on by default. Before a report is built, the address is checked twice:

1. **published ranges** — `src/abuseipdb_reporter/crawler_ranges.py`, generated by
   `tools/update_crawler_ranges.py` from the publishers' own machine-readable lists:

   | List | Ranges | Publisher's `creationTime` |
   |---|---|---|
   | Googlebot / InspectionTool / AdsBot / Storebot | 317 | 2026-10-30 |
   | GPTBot | 18 | 2026-09-22 |
   | OAI-SearchBot | 39 | 2026-01-02 |
   | ChatGPT-User | 235 | 2026-10-27 |

2. **reverse DNS with forward confirmation** — `crawl-…googlebot.com`,
   `msnbot-….search.msn.com`, `*.yandex.com|ru|net`, `*.applebot.apple.com`,
   `*.amazonbot.amazon`, `*.commoncrawl.org`, `*.bytedance.com`,
   `*.perplexity.ai`. The name is trusted only when it resolves **back** to the same
   address, which is the check Google and Bing document.

A match means: no API call, the event is finished locally, the skip is logged,
counted in `status.json` as `crawlers_skipped`, exported as
`abuseipdb_reporter_last_run_crawlers_skipped` and raised as a Zabbix trigger
(`Fail2Ban AbuseIPDB: a crawler was banned`, Warning) — because a skipped crawler
means **a fail2ban rule is wrong** and must be fixed, not silently tolerated.

```bash
abuseipdb-report --crawler-status              # which lists are loaded and when published
abuseipdb-report --crawler-check 66.249.66.5   # -> crawler (published google range)
abuseipdb-report --crawler-check 157.55.39.10  # -> crawler (verified: Bingbot (msnbot-...))
abuseipdb-report --crawler-check 8.8.8.8       # -> not a crawler (exit 1)
```

Turn it off with `never_report_crawlers = no`, or keep the ranges but drop DNS with
`crawler_rdns = no`.

### What the rail deliberately does not do

* **No user-agent trust.** A `Googlebot` string proves nothing — anybody can send it.
  Address-based checks only.
* **No broad ranges.** Apple publishes no list and its crawler lives in `17.0.0.0/8`;
  whitelisting that would whitelist a whole cloud. It is covered by reverse DNS
  instead. The same reasoning excludes "all of GCP" or "all of Cloudflare".
* **No claim about ClaudeBot.** Anthropic publishes neither a range nor a resolvable
  crawler name, so `ClaudeBot` cannot be recognised by address. The audit tool still
  sees it by user-agent in the logs; the documentation says so rather than implying
  coverage that does not exist.
* **No silent pass for a spoofer.** The rail protects the *report*, not the firewall:
  an attacker using a crawler name still gets banned and blocked, it simply is not
  named in AbuseIPDB under that identity.

## Keeping the firewall itself polite

The rail protects the public report. To make sure a crawler is not banned in the
first place:

* keep the filters path-based (they are), and do not add a user-agent jail;
* when a site needs `deny` rules, add `error_page 403` / a distinct status for
  crawler-relevant paths, or the `nginx-forbidden` jail will count them;
* put the narrow published ranges into `[DEFAULT] ignoreip` if you want fail2ban to
  skip them before the filter even runs:

  ```ini
  # /etc/fail2ban/jail.d/… — merge, do not overwrite, the existing ignoreip
  ignoreip = … 66.249.64.0/19 192.178.4.0/23 192.178.6.0/23 20.171.206.0/24 52.230.152.0/24
  ```

  `66.249.64.0/19` and the two `192.178.x` blocks are Google's crawler space; the
  `/24`s are GPTBot's. Do **not** add `34.0.0.0/8`, `35.0.0.0/8` or `20.0.0.0/8` —
  those are entire clouds, and banning a scraper that rents a GCP VM must still work.

## Repeating the check

```bash
scp tools/audit-good-bots.sh host:/tmp/ && ssh host 'bash /tmp/audit-good-bots.sh 7'
```

It prints the jail list, the crawler check for every banned address, the ignoreip
coverage, the per-bot status matrix over the access logs, and any nginx rule that can
target a crawler. Read-only, safe to run at any time; run it after changing a jail,
a `deny` rule or a rate limit.
