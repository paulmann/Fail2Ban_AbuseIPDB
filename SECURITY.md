# Security Policy

## Supported versions

| Version | Supported |
|---|---|
| 1.x | yes |

## Reporting a vulnerability

Please **do not** open a public issue for a security problem. Report it privately
through GitHub Security Advisories ("Security" → "Report a vulnerability") or by
contacting the maintainer directly. Include:

* affected version and commit;
* a reproduction (commands, configuration, expected vs. actual);
* impact assessment (what an attacker gains).

You will get an acknowledgement within a few days.

## Security design of this project

The reporter handles untrusted data (attacker IPs and log lines) and a secret
(the AbuseIPDB API key), so the following rules are intentional:

1. **No shell interpolation of log lines.** The fail2ban action receives only
   `<ip>`, `<name>`, `<bantime>` and `<failures>` - values generated by fail2ban.
   The matched log text (which contains attacker-controlled URLs) is read from
   fail2ban's SQLite database by the Python worker and is only placed inside the
   JSON/form comment. The stock `abuseipdb.conf` action interpolates `<matches>`;
   this project does not.
2. **Secret isolation.** The API key is stored in `/etc/abuseipdb/reporter.conf`
   with mode `600 root:root`, is not written to logs and is not part of the
   fail2ban configuration.
3. **Least privilege.** The worker runs as a oneshot systemd unit with
   `PrivateTmp=true`, `ProtectSystem=full`, `ProtectHome=true`,
   `NoNewPrivileges=true`; the only writable paths are `/var/lib/abuseipdb` and
   `/var/log`.
4. **Input validation.** Addresses are parsed with `ipaddress`; private,
   loopback, link-local, reserved and documentation ranges are never queued
   unless explicitly overridden (`--allow-reserved`, tests only).
5. **No PII in reports.** Attempted usernames, mail content and client domains
   are not sent. Reports are public and must contain only evidence about the
   attacker.
6. **Bounded remote interaction.** HTTP timeout, retry limit, daily/per-run
   budgets and a per-IP throttle prevent an abused or compromised host from
   flooding AbuseIPDB.

## Out of scope

* The firewall behaviour of fail2ban itself (the project does not change it).
* AbuseIPDB's own service and data.
* Credentials other than the AbuseIPDB API key.
